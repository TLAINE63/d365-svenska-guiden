# src/lib rules

- ISV catalogue rules: see src/lib/isv/AGENTS.md; Systemval handoff rules: see src/lib/systemval/AGENTS.md.
- Beslutsmognadsindex v2 and Demand Engine signals rules: see supabase/functions/_shared/AGENTS.md.
- Min D365-plan reuses buyerProfile and buyerContext, with d365Plan storing only local priorities and investigation area; keeps anonymous persistence without server data.
- Optional buyer accounts mirror the localStorage keys in accountSync.ts to buyer_saved_state (own-row RLS); server wins on login, so tools stay account-unaware.
- Requirement specs (ERP/Sales/Service/Marketing) restore and save industry, size and areas via useKravProfileSync in kravProfile.ts; URL/test prefill wins, profile is the fallback, so context survives any entry path.
- Calculators hand off to the product-matched requirement spec only via calcToKrav.ts URL params (bransch/storlek/omraden/produkt + kalla=kalkyl) that the specs already read; ambiguous calculator industries and user counts for ERP (asks employees) are never mapped, so prefill is never guessed.
- Existing-customer diagnosis (existingDiagnosis.ts) is deterministic with 8 needs, asks a follow-up only when it changes the next step, never auto-opens contact, and passes only a known product to partner search via ?apps=, so nothing is guessed.
- Second opinion (/second-opinion/) reuses PlanContactDialog advisory mode via a ContactTopic; diagnosis passes only a known need via ?behov= (unknown values ignored), so no parallel lead flow exists.
- Basic-profile SEO title/description come from partnerSeo.ts, shared by PartnerBasicProfile and the prerender fallback, so crawlers and visitors see identical metadata within 50/155 chars.
- Partner search (Sprint 1.1, /valjdynamics365partner/): need step, existing filters plus assignment type/delivery form/competence (src/lib/partnerSearchFilters.ts, reusing delivery profiles and extended competencies), neutral seeded order and two exits (Besök partnern to the partner site, or AdvisoryOffer placement partner_search creating an internal case) share src/lib/partnerSearchFunnel.ts; need and internal intent live only in sessionStorage and funnel events fire only after the search started in the visit, so tracking stays anonymous and commercial status never orders results.
- Expert path (Sprint 1.2, /kompetens/ and guides): role/product/specialism then seniority/industry/geography/delivery/start/length are kept as a session-only draft in src/lib/expertRequirement.ts (specialisms reuse partner-master taxonomy labels); ExpertRequirementExit submits via PlanContactDialog advisory placement expert_requirement, creating an advisory case with status ny, and buyer_approved_expert_introduction is logged only by the partner_introductions trigger after documented consent, so no parallel lead flow or automatic partner sharing exists.
- Existing customers (Sprint 1.3, /befintlig-kund/): ExistingDynamicsNextStep shows the six options from src/lib/existingDynamicsPaths.ts above the older symptom diagnosis; competence opens CompetenceChoiceDialog, and both exits reuse PlanContactDialog advisory (placements existing_dynamics and partner_relationship_review, the latter with initial_intent PartnerChange), so no parallel partner, competence or lead flow exists.
- Cost journey (Sprint 1.5): CostNextSteps (drivers, four next steps, exit) renders after the /kostnad/ quick estimate and below the implementation calculator, with shared options and anonymous events in src/lib/costJourney.ts; the exit reuses PlanContactDialog advisory placement cost_help, so cost help never creates a parallel lead flow or reaches partners.
- Next steps (Sprint 1.6): ContinueEvaluation renders "Fortsätt er utvärdering" only for pilot paths in src/lib/nextSteps.ts (max three own steps plus help last, each with cta type, conversion_type and recipient); help reuses PlanContactDialog advisory placement next_step_help, so new pages are added by config and nothing reaches partners.
- Buyer Assessment Light (Sprint 1.7): BuyerAssessmentLight in SolutionNeedStart (/kom-igang/) computes situation, questions, paths and next step deterministically in src/lib/buyerAssessment.ts before any contact field; "Diskutera bedömningen" reuses PlanContactDialog advisory placement solution_assessment with the summary as shared sections, so no score, Opportunity Type or partner sharing exists.
- No Dead Ends (Sprint 2.1): every public template gets a next step from src/lib/nextSteps.ts (pilot paths first, else TEMPLATE_NEXT_STEPS via ContinueEvaluation `template`); empty results use EmptyResultsNextSteps and Footer renders GlobalNextStepFallback, hidden by CSS `:has([data-next-step-block])` when the page already has a block, so help never appears twice and is never the only option. Report: docs/NO-DEAD-ENDS-2.1.md.
- Journey funnels (Sprint 2.2): trackFunnelEvent sends a companion `journey_funnel` event for every event mapped in src/lib/journeyFunnels.ts, and DB triggers log buyer_approved_introduction/meeting_requested/meeting_held via journey_log_event; JourneyFunnelsCard (funnel-stats journey_funnels) keeps self-service, contact to d365.se and mediated contact in separate columns, and the verification breakdown is analysis only, never ranking input. Map new events there instead of adding parallel trackers. See docs/FUNNELMATNING-2.2.md.
- CTA hierarchy (Conversion & Trust step 3): partner profile, comparison and competence labels come from src/lib/conversionCtas.ts; the secondary "Prata med d365.se" reuses AdvisoryOffer (partner_search on profiles, compare, expert_requirement), so no new placements or flows exist.
- Contact levels: every contact form fires contact_level_started/submitted via src/lib/contactLevels.ts (question, advisory, partner) next to its own events, and funnel-stats buyer_paths reports them per level, so the three conversion levels are always comparable.
- Kunskapscenter (WP1): four entry cards, recommendations, topic and situation metadata are derived in src/lib/knowledgeCenter.ts from existing item fields plus a short editorial id map, filtering the same allItems list as the library; INSIDE articles show as type intervju in that list, so no parallel library, taxonomy or lead flow exists (help reuses AdvisoryOffer next_step_help).
- Partner category tags (F&SCM, BC, CRM, Tillverkning) on /valjdynamics365partner/ come from src/lib/partnerCategoryTags.ts using only the partner's own products/industries; display and filter only, never ordering, so lists stay neutral.
- Lösningsvägval (standard/ISV/automation/egen/kombination) on /kom-igang/ via src/lib/solutionPath.ts + SolutionPathChoice; deterministic, insufficient input says so, help reuses MEETING_TOPIC (meeting_20min), so no parallel lead flow.
- AI agent competence extends the existing ai_profile (capabilities in src/lib/aiProfile.ts AGENT_CAPABILITY_KEYS); basis "reviewed" comes only from admin-set information_status, never the partner's own evidence tick, and the search filter only narrows when chosen, so missing data never reads as missing skill and ranking stays neutral.
- Agent readiness (src/lib/agentReadiness.ts) lives inside Lösningsvägval, shown only when automation is primary or an alternative; it reuses taskType/approval/ownership/criticality, adds three questions with "Vet inte", returns one of three modes (or insufficient) with max three next steps starting with standard/ISV comparison, so it never becomes a separate AI test or a build recommendation.
- Download forms share DownloadContactOptIn + downloadConsent.ts (never pre-ticked); only leads.consent_contact = true downloads export to Demand Engine as nedladdning, so plain downloads stay anonymous domain events.

- Redaktion remember preference expires after 30 days; editor-session revalidates roles on entry and foreground renewal, never extending the HMAC token to 30 days.
