# src/lib ISV rules

- Product pages use isvPresentation entitlements and the public build snapshot without contacts, stable product IDs and reviewed product-specific evidence; supplier submissions cannot mark evidence reviewed, so presentation never alters verification or relevance.
- Premium product openings reuse productExposure (verified plus Presence); basic openings stay compact and light, while previews use real media or existing facts, never fabricated content.

- ISV catalogue (Sprint 1.9): isv_vendors (vendor) 1→N isv_solutions (product), each with its own source/confirmation/verification fields; a DB trigger derives information_status (verified, vendor_confirmed or compiled; only verification_status verified makes it verified), so premium, agreements or a verified vendor never verify a product. Vendor contacts and agreement status live in service-only isv_vendor_internal. Vendor self-service reuses /isv-profil/:token (scope vendor) and isv_submissions (kind vendor_profile/solution_update/new_solution), applied only on admin approval; the catalogue's help exit reuses PlanContactDialog advisory placement isv_product_help, and labels, filter and anonymous isv_* events live in src/lib/isvInformationStatus.ts.
- ISV industries: catalogue filter and labels map free vendor tags to the 21 /branscher/ industries via src/lib/isvIndustries.ts (display only, stored tags untouched; non-industry tags never map), with shared images in src/data/industryImages.ts and product logos/official names in src/data/d365ProductBranding.ts, so the catalogue and /branscher/ always match.
- ISV catalogue filters: product groups (ERP, CRM och kundmöte, Fler appar) live in src/lib/isvProductGroups.ts; BcIsvCatalog counts every facet against all other active filters (skip own facet), and industry stays an optional step, so counts never promise hits that disappear and generic solutions are not hidden.
- ISV buyer needs: catalogue need buttons group technical categories into Swedish buyer needs with search synonyms in src/lib/isvBuyerNeeds.ts (display/filter only, stored categories untouched; every category maps to exactly one need, tested), so new categories need one mapping line.
- Product pages' ISV section (ProductIsvSection) shows top need areas with one example plus a few more per area, max one per vendor; an editorial per-product list in src/lib/isvCommonExamples.ts orders examples first, so examples reflect editorial judgement and never commercial status.
- ISV exposure: src/lib/isvVisibility.ts decides logo/website/contact (product logo first, else vendor logo) (products need both D365 Verifierad and active ISV Presence (premium_product); vendors matching a featured partner count as verified), and public ISV contacts come only from the security-definer RPC public_verified_isv_contacts (vendors/published products that are verified AND have ISV Presence; a product without its own sales contact inherits the vendor contact), so unverified contact data never leaves service-only tables. businesscentral.se syndication (bc_isv_products_v1) also requires both. Public facts (model, countries, target size, price) come only from RPC public_isv_product_facts and render via IsvProductExtras only when filled; demo video and customer cases are admin-edited fields on isv_solutions.
- ISV vendors that are also Solution Partners set isv_vendors.partner_slug; export-isv-products emits linked_partner_slug/company_key so CRMs merge one company, never used for ranking.
